# Shell appearance

Hypergolic Glass carries an orbital horizon, a fine ignition line, square frames
and restrained orange accents into the existing multi-napplet shell. The product
spark remains the logo. The native shell follows system light and dark appearance.

## Visual system

`src/shell/palette.ts` owns the shared colors. Dark appearance uses blue-black
surfaces; light appearance uses a white background with subtle cool-gray surfaces. Primary actions use the
foreground color, and orange marks focus, progress and trusted requests. Palette
regressions require WCAG AA contrast for body, secondary and accent text across
all three surfaces and for action labels.

Barlow supplies display and body text. JetBrains Mono is reserved for public keys,
addresses and technical values. Both are bundled locally with their original OFL
licenses; the shell remains usable with system fonts if font loading fails.
Headings can use uppercase visually while preserving the original accessible
napplet name. Body copy uses sentence case and system text scaling.

The backdrop uses small compressed PNG layers generated by
`scripts/generate-shell-artwork.py`. It has no animation, blur, input handling or
accessibility elements. Its orbital composition remains on entry, the shelf and
trusted shell surfaces. A focused napplet uses a solid background so the shell
recedes without changing the napplet's own content.
`FrameCorners`, `TrustedBand`, `ShellPressable` and `ShellTextInput` apply shared
frame, request, touch-target and focus treatment. Controls provide pressed and
disabled feedback and at least a 44-point target.

## Interaction

The two-column live overview preserves opening order, retained instances and edge
gestures. An empty workspace explains the next step and offers Open a napplet.
The focused shell uses one 44-point control row plus its one-point divider. The
24-point spark opens All napplets; the plain centered napplet name (no arrow) opens a square framed
menu with All napplets, Settings and Close napplet. The avatar opens Settings and
keeps the full public key in its accessible label. The full copyable key remains in
Settings; the expanded shelf header keeps the short npub. Menu dismissal restores
focus to its title control. Android Back dismisses the menu before workspace
navigation. Close checks, unsaved-work warnings and generation ownership retain
their existing behavior.

A loaded napplet has no outer border or corner brackets. The outer stage inset is
six points with two points below it; the host reserves a 14-point gutter on each
side for the visible swipe tabs. The all-napplets cards, menus and other shell
surfaces retain their square borders and corner brackets, alongside the orbital
artwork and trusted request bands. This follows the owner's clarified distinction
between a borderless loaded view and the framed shell navigation. At
standard text size this removes about 74 points of vertical shell overhead and
adds ten points of guest width compared with the first Glass layout; system safe
areas and napplet content remain independent.

Inset swipe tabs stay in the lower third. Each neutral 14-by-64-point tab has a
44-by-88-point gesture target. Border and grip turn orange on contact, including a
tap, then return to neutral. A shorter, quieter grip marks an end of the loaded
list. Tap opens the overview; an inward drag switches to the adjacent napplet and
stops at the first or last one. The existing vertical overview gesture, cancellation
and accessible actions remain. The transparent part of each target extends inward;
guest touch input outside those targets remains available. Small visible tabs do
not imply smaller touch targets. Android uses a native gesture-exclusion rectangle
for each active handle's 44-by-88-point target so system Back cannot intercept the
inward swipe there. Exclusions clear when handles are disabled or detached; the
rest of either edge retains system Back. This follows Android's
[selective gesture-conflict guidance](https://developer.android.com/develop/ui/views/touch-and-input/gestures/gesturenav).

Settings keeps address opening near the top and groups the remaining controls into
Identity, Connections, Napplet access and Developer tools. Inputs retain native
keyboard and secure-entry behavior. Address validation explains how to correct
invalid input. A pending lookup can be cancelled; verification status describes
actual work performed by the existing resolver.

Trusted review sheets use an edge-to-edge orange band, scrollable content and
reachable actions. Event bodies, publishers, identities, destinations and exact
request details remain available. These controls present existing authority;
the visual band does not grant a capability or verify a publisher by itself.

Napplets own their content and typography. Those using the existing theme service
receive the shared background, text and accent colors. The host reads system
appearance and delivers changes through Kehto's existing `publishTheme` path,
including its recipient checks. Service state updates before delivery, and its
media-query listener is removed when the generation is torn down. No wire fields,
grants or trust policy change.

## Native presentation fixture

`tests/native/ui-style/index.tsx` composes real shell components with an isolated
public identity and the real local runtime. It has no signer, secret import or
publication. Its three fixture controls open an empty workspace, the bundled UX
Lab workspace, and a presentation-only signing review. Ordinary production entry
continues through `index.ts`.

The XCTest `ui-style` scenario uses `org.nostrocket.hypergolic.uistyle`. The Android
driver in the same fixture directory accepts only an explicit emulator serial and
the same isolated app ID. They exercise the empty state, invalid address feedback,
grouped settings and masked import field, workspace navigation, the title menu,
menu dismissal, close protection
and a truthful sample review. Evidence includes screenshots and native hierarchy
captures. These checks establish UI behavior in simulated devices; they do not
establish protected-key storage, signing or physical-device acceptance.

For a native iOS fixture build, follow the separate-bundle-ID workflow in
[development](development.md), using `ENTRY_FILE=tests/native/ui-style/index.tsx`.
Run the existing iOS driver with scenario `ui-style`. Android fixture builds use a
separate application ID and Expo's `jsMainModulePath` pointing to
`tests/native/ui-style/index`; restore generated project files afterward. Metro
serves that source entry. Run `python3 tests/native/ui-style/android.py --serial
EMULATOR_SERIAL --output NEW_EVIDENCE_DIRECTORY --appearance dark` and repeat for
light appearance and `--font-scale 1.5`. Keep evidence outside source.

## Asset and dependency provenance

Barlow originals come from `google/fonts/ofl/barlow`; JetBrains Mono comes from
`JetBrains/JetBrainsMono/fonts/ttf`. Their original licenses are kept beside the
fonts and packaged in both native products under `shell-notices`. The same folder
includes Expo System UI's original MIT license.

Expo Font 57.0.3 becomes an explicit dependency at its already installed version.
Expo System UI 57.0.3 enables Android's automatic appearance setting. Its Android
archive resolves AppCompat and AppCompat Resources to 1.7.1. The selected archive
inventory records these exact hashes, retaining all other selected artifacts.
Both new AndroidX archives contain no embedded license/notice files or native
images; the existing AndroidX license text remains packaged. The existing native
notice guards are unchanged.

The normal Android and iOS Metro source maps each identify 61 package contributors,
adding Expo Font's original MIT notice. The manifests record the reviewed Metro
bundle and source-map hashes, 57 original notice files and four shared-notice
packages. These are attribution receipts for exported JavaScript, not a statement
that those bytes are a signed release APK or iPhone application.
